# 图形清理（PURGE / OVERKILL）功能设计分析

> 本文记录「新增图形清理功能」的**深度思考过程**：从需求动机出发，推演垃圾图元判定、
> 重复图元等价判定与合并算法、分桶加速、统计输出与撤销事务设计，最后沉淀经验教训。
> 目标读者是后续维护者——读完应能理解「为什么这样设计」而非仅「改了哪里」。

---

## 1. 需求拆解与动机

用户原始诉求可拆为四层：

1. **垃圾检测**：长期编辑后自动检测并清除**不可见的垃圾图元与冗余数据**，防止文件体积持续膨胀；
2. **重复清理**：实现重复图元清理逻辑（类似 AutoCAD **OVERKILL**），自动识别并**合并或删除**完全重合、重叠的线段与圆弧等几何对象；
3. **安全边界**：清理需**保留有效实体与用户编辑内容**，不破坏原有图形结构；
4. **可观测**：执行前后输出**图元数量对比统计**；并把深思过程输出为 md 文档。

### 1.1 图面"浮肿"的真实来源

在一个支持复制粘贴、块插入、导入导出、自动追踪的 CAD 系统里，文件体积随编辑次数增长几乎是必然的：

- **垃圾图元**：拖拽/修剪/打断残留的零长线段、半径 0 的圆、被剪成空的多边形、
  导入时的 NaN 坐标、空文字——它们**渲染不可见**，却占文件体积、参与命中检测、
  参与 DXF/DWG 导出（导出后成为下游系统的脏数据）。
- **重复图元**：多次复制-粘贴到同一位置、多次导入同一图形、自动追踪与手绘叠加——
  完全重合的线段/圆/弧；或首尾相接的**共线重叠**线段（视觉上一条线，数据上 N 条）。
- **冗余数据**：删除最后一个块引用后残留在块表里的**无引用块定义**；删光图元后残留的**空图层**。

这与既有 purge 类工具（如 AutoCAD 的 PURGE / OVERKILL）面对的是同一类问题，
但本系统的数据模型是自研的（`Element` 统一结构 + `SketchModel` 表驱动），需要一套贴合自身结构的实现。

---

## 2. 设计目标与约束

| 目标 | 说明 |
|------|------|
| 安全第一 | 绝不删除"看起来正常"的图元；判定阈值全部可配置、可预览 |
| 可撤销 | 图元增删走一次 `beginEdit + applyChanges`（一次 Ctrl+Z）；块/图层清除各自独立撤销 |
| 不破坏结构 | 图层归属、块引用、标注/约束的 id 引用关系不被清理动作打断 |
| 可观测 | 执行前后总数对比 + 按类型删除明细 + 每条删除/合并的可读说明 |
| 最小侵入 | 不改 `Element` 结构、不改渲染/序列化管线，纯核心层新增 `Cleanup` 模块 + 一个对话框 |

---

## 3. 核心设计决策（含推演）

### 3.1 决策一：把"垃圾"定义为「退化/无效/不可渲染」，而非「不可见」

**推演**：需求说"清除**不可见的**垃圾图元"。字面理解有两种：

- 甲：删除所有 `visible == false` 的图元 —— **危险**。用户可能有意隐藏图元（`setLayerVisible`、
  属性面板关可见性都是合法编辑），直接删除等于破坏用户编辑内容，违反需求 3。
- 乙：删除**退化到根本画不出来**的图元（零长线、零径圆、NaN 坐标、空文字、空多边形）——
  这些图元"不可见"是因为**没有可见内容**，删除它们不影响任何视觉效果。

**决策**：默认走乙（`purgeGarbage`，默认开）；甲作为独立开关 `purgeInvisible`（默认**关**），
并在 UI 上明确标注【可能移除有意隐藏的内容】，把风险交给用户显式选择。

这是"需求意图"与"用户数据安全"冲突时的标准解法：**把字面要求映射到安全语义，
把不安全的那部分做成显式 opt-in**。

**退化判定表**（`isGarbage`，全部阈值来自可配置容差 `tol`）：

| 类型 | 判定为垃圾的条件 |
|------|------------------|
| 全部 | 任一坐标 NaN/inf；radius/radiusY NaN/inf |
| Line | `pts.size() < 2`；或两端点距离 ≤ tol（零长） |
| Circle | `radius ≤ tol` |
| Arc | `radius ≤ tol`；或起止角几乎相等**且非整圈 360°** |
| Ellipse | `radius ≤ tol` 或 `radiusY ≤ tol` |
| Rect/Poly/Hatch/Boundary | `pts.size() < 3`；或面积 ≤ tol²（近零面积，shoelace） |
| Polyline/Spline | `pts.size() < 2` |
| Text | 文本 trim 后为空（无内容可渲染） |
| BlockRef/Dimension/Constraint/Xline | 保守保留（default 不删） |

⚠️ **Arc 整圈陷阱**：`endAngle − startAngle = 360` 是"整圆弧"的合法表达，不能用
`wrapDeg360` 归一化后再判相等——`wrapDeg360(360) == 0` 会把合法整圆误判为零弧。
必须比较**原始差值**：`|d| ≤ tol` 且 `‖|d| − 360‖ > tol` 才算退化。

### 3.2 决策二：OVERKILL 的两种等价语义——「完全重合」删除 vs「共线重叠」合并

**推演**：OVERKILL 对两条线段的处理在真实 CAD 里分两档：

- **完全重合**（两端点重合，允许方向相反）：图元级冗余，直接删掉一份即可，零信息损失。
- **共线重叠**（在同一条无限直线上、投影区间有交叠但不完全重合）：各自都有一部分独占信息，
  删谁都会丢内容 → 必须把两段**合并成一段**（取投影区间的整体 min/max 为新端点）。

**决策**：两类都实现。`typeEquiv` 对 Line 先判完全重合（`lineEquiv`），不重合再尝试
`tryMergeLines`；合并成功则产出"删 2 加 1"的三条 Change（净减 1 个图元），继承 a 的全部样式。

**共线合并的三个必要条件**（缺一不可，全部满足才合并）：

1. **近平行**：两方向单位向量 `|cos| ≈ 1`（容差 ±2.5°，`1e-3`）；
2. **共线**：每个端点到对方无限直线的距离都 ≤ tol；
3. **区间交叠或相邻**：两段在共线轴上的投影区间满足 `max(minA,minB) ≤ min(maxA,maxB) + tol`
   ——否则只是同一条无限直线上的**两段分离线段**（用户有意画的），合并会把中间的"空隙"填上，
   破坏图形结构。这一条是安全边界的关键。

### 3.3 决策三：各类型等价判定的覆盖范围与「明确不参与」名单

| 类型 | 等价判定 |
|------|----------|
| Circle | 圆心距 ≤ tol 且半径差 ≤ tol |
| Arc | 圆心/半径同上，且起止角 (mod 360) 正向或反向匹配 |
| Ellipse | 圆心 + 长半轴 + 短半轴 + 长轴角 (mod 360) |
| Rect/Polygon | 顶点序列等价（闭合：允许循环移位 + 反向） |
| Polyline/Spline | 顶点序列等价（开放：正向或反向；闭合：同上） |
| Hatch/Boundary | 外环等价 + 内孔集合等价（逐孔匹配） |
| Text | 位置 + 文本内容 + 字高 |
| Xline | 通过点 + 方向角 (mod 360) |
| **BlockRef** | **不参与**——多个同参块引用往往是**有意的重复**（螺栓阵列、门窗复制），删了就是破坏图形 |
| **Dimension / Constraint** | **不参与**——携带 refA/refB 的 id 引用，删除/合并会使引用悬空 |

**推演**：这最后一行是最容易被忽略的坑。AutoCAD OVERKILL 同样默认不动块引用与标注。
把"几何上相同"与"语义上冗余"区分开，是本功能"不破坏原有图形结构"的核心保障。

### 3.4 决策四：重复对的保留策略——按 GB/T 14665 重合图线优先顺序

两条完全重合的线段必须删一条，删谁？**决策**：复用项目里已有的
`linePriority()`（GB/T 14665-2012 4.3「重合图线优先顺序」：可见轮廓粗实线 > 不可见轮廓虚线 >
轴线点画线 > 假想轮廓 > 断裂线）：

1. 线型优先级高者保留（粗实线压过被它盖住的虚线——视觉结果不变）；
2. 优先级相同则可见者保留；
3. 再同则 id 小者（先画的）保留。

这样"清理后图面视觉零变化"有了标准依据，而不是任选其一。

### 3.5 决策五：分桶把 O(n²) 压到近似 O(n)

两两比较全图是 O(n²)，几千图元的图会明显卡顿。**决策**：为每个图元计算一个**分桶键**：

```
key = type | q(bbox.minX) | q(bbox.minY) | q(bbox.maxX) | q(bbox.maxY) [| q(radius)...]
q(v) = round(v / s) * s,  s = max(tol × 50, 1e-3)
```

- 完全重合的两图元 bbox 逐坐标相同 → 同键；
- 共线重叠的两线段 bbox 差在 tol 量级 → 同键（s = 50·tol 有 50 倍余量）；
- 圆/弧附加半径键、椭圆附加双半轴键，避免同 bbox 不同径的误聚。

只在同桶内做两两比较。重复图元必然同桶 → 召回不损失；不同桶必然不重合 → 正确性不损失。
这正是"**哈希粗筛 + 精判**"的经典结构：把昂贵的几何判定只花在真正可能重复的对上。

### 3.6 决策六：统计输出——三层粒度

**决策**：`CleanupStats` 提供三层：

1. **一行对比摘要**（对话框结果区 + 模型日志各一份）：
   `图形清理：图元 1200 → 1130（移除 70：垃圾 12 / 重复 45 / 合并 13；冗余块 2 / 空图层 0）`
2. **按类型明细**：`removedByType`（`map<ElementType,int>`），供后续扩展成表格；
3. **逐条说明**：`detail` 每条删除/合并一行（含 id、类型、原因），在对话框列表里完整展示，
   让用户在执行后可以逐条核对、必要时 Ctrl+Z 回退。

其中合并计数的语义：**每次合并净减 1 个图元**（删 2 加 1），所以
`totalAfter = totalBefore − garbage − dupDeleted − merged`。
这个恒等式写进了实现，是统计正确性的自查锚点。

### 3.7 决策七：撤销事务——图元一处、块/图层各自独立

**推演**：`modify::applyChanges` 本身**不压撤销快照**（约定调用方先 `beginEdit`），
它内部全走 Quiet API。而 `removeBlock` / `removeLayer` **各自内部压自己的快照**。
于是有两种组合：

- 甲：`beginEdit` → `applyChanges`（图元）→ `removeBlock/...`（块/图层）
  → 得到 1 + n + m 个撤销步，每一步都可独立撤销、状态一致，多次 Ctrl+Z 完整还原；
- 乙：追求"一次 Ctrl+Z 全还原"需要块/图层的 Quiet 删除 API（当前不存在），
  为此新增 API 属于为边际收益扩面。

**决策**：取甲。块/图层清理本来就是低频且独立语义的操作，与其为单步撤销新增模型 API，
不如接受"图元清理一步撤、块/图层清理各自一步撤"——每一步都可逆、无中间损坏态。
预览（`dryRun`）则完全不改模型，先看数字再决定是否执行。

### 3.8 决策八：对话框交互——先预览后执行

**决策**：`CleanupDialog` 提供「预览统计」（`dryRun=true`，只算不改）与「执行清理」两按钮。
预览走与执行**完全同一份** `runCleanup` 代码（仅 dryRun 标志不同），杜绝"预览说有、执行说无"
的统计漂移——这是**单一实现路径**原则在清理语义上的应用：预览即执行的计划阶段。

## 5. 用户工作流

1. 长期编辑后（或打开外来导入图后），点【修改 > 图形清理...】；
2. 勾选清理项（默认：垃圾图元 ✓ / 无引用块 ✓ / OVERKILL ✓；隐藏图元与空图层默认关）；
3. 点「预览统计」→ 查看对比数字与逐条明细，必要时调整容差再看；
4. 点「执行清理」→ 图元增删一次可撤；对话框展示执行后统计，供留档核对；
5. 若结果不合预期：Ctrl+Z 撤回图元部分（块/图层再各撤一步），调小容差重来。

## 7. 关键经验沉淀

1. **"不可见"的安全语义**：把"清除不可见图元"映射为"清除不可渲染的退化图元"，
   `visible=false` 的删除做成显式 opt-in——需求意图与数据安全冲突时的标准解法。
2. **几何上相同 ≠ 语义上冗余**：BlockRef（有意阵列）、Dimension/Constraint（id 引用）必须
   排除在 OVERKILL 之外，否则"清理"本身就成了破坏图形结构的操作。
3. **合并的安全条件是"区间交叠"**：共线但分离的两段线是有意留空的间隙，填上就是破坏图形。
   "近平行 + 共线 + 区间交叠"三条件缺一不可。
4. **整圆弧陷阱**：`wrapDeg360(360) == 0`，退化判定必须用原始角度差并显式排除 360°。
5. **预览与执行同路径**：同一 `runCleanup` 以 dryRun 标志区分，杜绝统计漂移；
   统计恒等式 `after = before − garbage − dup − merged` 作为自查锚点。
6. **哈希粗筛 + 精判**：分桶键（量化 bbox + 半径）把 O(n²) 压到近似 O(n)，
   且召回与正确性都不损失——重复检测类问题的通用结构。
7. **撤销事务的现实折中**：`applyChanges` 无快照、`removeBlock/removeLayer` 自带快照，
   两者混用必然多步撤销；与其为单步撤销扩模型 API，不如接受多步可逆。
