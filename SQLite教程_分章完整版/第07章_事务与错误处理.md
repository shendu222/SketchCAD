# 第 7 章 事务、错误处理与常用实践

## 本章目标

- 理解 SQLite 隐式事务机制，掌握显式事务提速的原理与写法；
- 建立完整的错误处理套路：错误码、errmsg、典型错误案例；
- 了解数据库锁与 `busy_timeout`，让多进程并发不再"database is locked"；
- 收集一组生产常用 PRAGMA 与工程实践清单。

## 7.1 事务：从 30 秒到 0.3 秒

**每个写语句默认各自构成一个隐式事务**：语句执行前后各做一次落盘同步（journal 创建/删除、fsync）。循环插入 1000 行 = 1000 次事务 = 1000 次磁盘同步——这就是慢的根源。

显式事务把它们合并成一次同步：

```c
sqlite3_exec(db, "BEGIN", NULL, NULL, NULL);       /* 开事务 */

for (int i = 0; i < 1000; i++) {
    sqlite3_bind_text(stmt, 1, names[i],  -1, SQLITE_TRANSIENT);
    sqlite3_bind_text(stmt, 2, phones[i], -1, SQLITE_TRANSIENT);
    sqlite3_step(stmt);
    sqlite3_reset(stmt);
}

sqlite3_exec(db, "COMMIT", NULL, NULL, NULL);      /* 提交：此刻才真正落盘 */
```

实测（第 5 章练习 4 的基线程序加事务）：机械盘上 1000 行插入通常从 20~30 秒降到 0.1~0.3 秒，**两个数量级**。

### 回滚与原子性

事务的另一半价值是**原子性**——要么全成功，要么全不留痕：

```c
int ok = 1;
sqlite3_exec(db, "BEGIN", NULL, NULL, NULL);
for (/* 批量操作 */) {
    if (sqlite3_step(stmt) != SQLITE_DONE) { ok = 0; break; }
    sqlite3_reset(stmt);
}
sqlite3_exec(db, ok ? "COMMIT" : "ROLLBACK", NULL, NULL, NULL);
```

出错即 `ROLLBACK`，已执行的部分整体撤销。**"转出/转入必须同时成功"式的业务逻辑，必须靠事务表达**，靠应用层补偿代码既繁琐又不可靠。

### 嵌套与 SAVEPOINT

SQLite 不支持标准嵌套事务，但支持保存点——事务里打"书签"：

```sql
SAVEPOINT sp1;
-- 若干操作
ROLLBACK TO sp1;   -- 撤销到书签，事务本身继续
RELEASE sp1;       -- 确认书签之后的操作
```

### 顺手一提：WAL 模式

```sql
PRAGMA journal_mode = WAL;   -- Write-Ahead Logging
```

默认回滚日志模式下**读写互斥**；WAL 模式下**读写可并发**（写仍单线程），桌面软件多线程场景强烈建议在连接后立刻执行这条 PRAGMA。代价是数据库目录多出 `*-wal`/`*-shm` 两个伴随文件，属正常现象，勿删。

## 7.2 错误处理的标准姿势

### 三层信息

```c
int rc = sqlite3_step(stmt);
if (rc != SQLITE_ROW && rc != SQLITE_DONE) {
    /* 第一层：错误码 */
    printf("错误码: %d\n", rc);                       /* 如 SQLITE_CONSTRAINT = 19 */
    /* 第二层：扩展错误码（看第几个约束失败） */
    printf("扩展码: %d\n", sqlite3_extended_errcode(db));
    /* 第三层：人话描述 */
    printf("信息: %s\n", sqlite3_errmsg(db));
}
```

常见错误码速查：

| 错误码 | 值 | 含义与对策 |
| --- | --- | --- |
| `SQLITE_OK` | 0 | 成功 |
| `SQLITE_BUSY` / `SQLITE_LOCKED` | 5 / 6 | 库被占用（见 7.3） |
| `SQLITE_CONSTRAINT` | 19 | 违反约束：唯一/非空/外键/CHECK，看 errmsg 定位具体列 |
| `SQLITE_READONLY` | 8 | 对只读连接执行写操作 |
| `SQLITE_CORRUPT` | 11 | 文件损坏，立即停止写入、从备份恢复 |
| `SQLITE_FULL` | 13 | 磁盘满 |

**`SQLITE_CONSTRAINT` 下的扩展码**：`SQLITE_CONSTRAINT_UNIQUE`（2067）、`SQLITE_CONSTRAINT_NOTNULL`（1299）等，能直接区分是哪类约束失败，配合 `sqlite3_errmsg` 里的列名即可精确定位。

### 完整的错误处理模板

```c
static int db_exec_stmt(sqlite3 *db, const char *sql)
{
    sqlite3_stmt *stmt = NULL;
    int rc = sqlite3_prepare_v2(db, sql, -1, &stmt, NULL);
    if (rc != SQLITE_OK) goto fail;

    rc = sqlite3_step(stmt);
    if (rc != SQLITE_DONE) goto fail;

    sqlite3_finalize(stmt);
    return SQLITE_OK;

fail:
    fprintf(stderr, "SQLite 错误 %d: %s\n", sqlite3_errcode(db), sqlite3_errmsg(db));
    sqlite3_finalize(stmt);   /* finalize NULL 是安全的 */
    return rc;
}
```

三个习惯值得固化：**每次 prepare/step 都检查返回值**；`sqlite3_finalize(NULL)` 安全，可放心统一收尾；日志里**同时**记错误码和 errmsg（错误码可编程分支，errmsg 可人工定位）。

## 7.3 并发与 database is locked

SQLite 的写锁以**库**为单位：任一时刻只有一个写入者。CLI 窗口开着未提交的写事务、另一个程序再来写，就会得到 `SQLITE_BUSY`，CLI 里表现为 `Error: database is locked`。

第一道解法——**忙等待超时**，连接后设置一次：

```c
sqlite3_busy_timeout(db, 3000);   /* 遇锁自动重试至多 3 秒，再不行才返回 SQLITE_BUSY */
```

多数偶发冲突在几百毫秒内自行消解，3000ms 足以消灭绝大多数报错。仍锁的场合再查三件事：

1. 是否有别的进程开着长事务（包括你自己的 CLI 会话）？
2. 多线程共用**同一个连接**且在不同线程同时用？——SQLite 默认"单连接串行"模式，最简单的合规做法是**每个线程一个独立连接**（同一进程内各连接并发读写同库在 WAL 模式下表现良好）；
3. 读写频繁争用？确认已开 WAL（7.1）。

进阶主题（多线程 API 模式、共享缓存）超出本书范围，记住两条底线即可：**每个线程独立连接 + WAL + busy_timeout**，能覆盖桌面软件的绝大多数并发需求。

## 7.4 常用 PRAGMA 与工程清单

| PRAGMA | 作用 | 建议 |
| --- | --- | --- |
| `PRAGMA journal_mode = WAL;` | 读写并发 | 桌面软件默认开 |
| `PRAGMA foreign_keys = ON;` | 启用外键约束（**默认关闭**！） | 建了外键的库必开，每连接一次 |
| `PRAGMA synchronous = NORMAL;` | 落盘同步级别 | WAL 下 NORMAL 足够安全且更快 |
| `PRAGMA busy_timeout` | 同 `sqlite3_busy_timeout` | 3000ms 起步 |
| `PRAGMA table_info(表名)` | 查列定义 | 调试用 |

```c
/* 连接初始化模板（本书最终推荐） */
sqlite3 *db;
sqlite3_open("contacts.db", &db);
sqlite3_busy_timeout(db, 3000);
sqlite3_exec(db, "PRAGMA journal_mode = WAL;"
                 "PRAGMA foreign_keys = ON;"
                 "PRAGMA synchronous = NORMAL;", NULL, NULL, NULL);
```

**工程实践清单：**

- 打开数据库后立刻执行初始化 PRAGMA 组（如上模板）；
- 所有外部输入走绑定（第 6 章），DDL 与迁移脚本才用 `exec`；
- 批量写必须包事务；
- `CREATE TABLE IF NOT EXISTS` 幂等建表，程序每次启动放心执行；
- 版本迁移：建一张 `PRAGMA user_version`（整型，`PRAGMA user_version = 2` 可读写）存结构版本号，启动时比对升级——轻量项目够用的"迁移框架"；
- 定期备份：小库用 `.dump` 或 `sqlite3 db ".backup backup.db"`；线上库用官方 Backup API；
- 数据库文件**不要**放在用户无权限或会被同步盘实时同步干扰的目录。

## 本章小结

- 隐式事务是批量写慢的根源，`BEGIN...COMMIT` 包住批量操作可提速百倍，出错用 `ROLLBACK` 保原子性；
- 错误处理三层：`errcode` / `extended_errcode` / `errmsg`；`SQLITE_CONSTRAINT`（19）配扩展码精确定位约束类型；
- `database is locked` 三板斧：`busy_timeout` + 每线程独立连接 + WAL 模式；
- 连接初始化模板：WAL + foreign_keys + synchronous=NORMAL；`user_version` 做轻量结构迁移。
